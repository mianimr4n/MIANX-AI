    40→# 2. Database Principles
    41→
    42→## 2.1 Tenant isolation is mandatory
    43→
    44→Every tenant-owned resource must have a clear path back to an
    45→organization.
    46→
    47→For most tenant-owned tables:
    48→
    49→``` text
    50→organization_id → organizations.id
    51→```
    52→
    53→## 2.2 Database security is not optional
    54→
    55→Tenant isolation must not depend only on frontend filtering or
    56→application code.
    57→
    58→PostgreSQL RLS will be part of the security boundary.
    59→
    60→## 2.3 Core and Domain data stay separated
    61→
    62→Mianx Core owns platform data.
    63→
    64→Domains own industry-specific data.
    65→
    66→Example:
    67→
    68→``` text
    69→CORE
    70→organizations
    71→memberships
    72→roles
    73→permissions
    74→domains
    75→modules
    76→subscriptions
    77→agents
    78→workflows
    79→audit_logs
    80→
    81→POULTRY DOMAIN
    82→farms
    83→sheds
    84→flocks
    85→feed_records
    86→mortality_records
    87→...
    88→```
    89→
    90→## 2.4 Avoid premature generic tables
    91→
    92→We will not put every future domain into a giant generic `business_data`
    93→table.
    94→
    95→Where relational structure matters, use real typed tables.
    96→
    97→## 2.5 Foreign keys are first-class
    98→
    99→Relationships must be enforced at the database level wherever
   100→appropriate.
   101→

   104→# 3. Tenancy Model
   105→
   106→The primary tenant is an **Organization**.
   107→
   108→``` text
   109→Mianx Platform
   110→      │
   111→      ├── Organization A
   112→      │      ├── Users
   113→      │      ├── Teams
   114→      │      ├── Domains
   115→      │      ├── Modules
   116→      │      └── Business Data
   117→      │
   118→      └── Organization B
   119→             ├── Users
   120→             ├── Teams
   121→             ├── Domains
   122→             ├── Modules
   123→             └── Business Data
   124→```
   125→
   126→Organization A must never be able to access Organization B's data.
   127→
   128→------------------------------------------------------------------------
   129→
   130→# 4. Organization Hierarchy
   131→
   132→The initial hierarchy is:
   133→
   134→``` text
   135→Organization
   136→    ↓
   137→Business / Brand
   138→    ↓
   139→Branch / Location
   140→    ↓
   141→Department / Team
   142→    ↓
   143→Users
   144→```
   145→
   146→Not every customer needs every level.
   147→
   148→The Core must therefore support optional hierarchy rather than forcing
   149→every organization to create brands, branches and departments.

   196→locale
   197→currency
   198→created_at

   203→
   204→``` text

   934→# 32. RLS Strategy
   935→
   936→RLS policies must be designed around organization membership.
   937→
   938→Conceptual authorization function:
   939→
   940→``` text
   941→user_has_org_access(authenticated_user, organization_id)
   942→```
   943→
   944→The policy pattern is:
   945→
   946→``` text
   947→authenticated user
   948→      ↓
   949→organization membership
   950→      ↓
   951→organization_id
   952→      ↓
   953→resource access
   954→```
   955→
   956→Example conceptual policy:
   957→
   958→``` text
   959→A user may SELECT a row
   960→IF
   961→the authenticated user has an active membership
   962→in the row's organization.
   963→```
   964→
   965→This is a design pattern, not final SQL.
   966→
   967→------------------------------------------------------------------------
   968→
   969→# 33. RLS Rules
   970→
   971→Every tenant-owned exposed table should answer:
   972→
   973→1.  What organization owns this row?
   974→2.  How does the authenticated user prove membership?
   975→3.  What role/permission is required?
   976→4.  Does the action require additional resource-level authorization?
   977→5.  Can an AI agent perform the same action?
   978→6.  What should happen to system/background jobs?
   979→
   980→No table should be considered complete until these questions are
   981→answered.
   982→
   983→------------------------------------------------------------------------
   984→
   985→# 34. RLS Performance
   986→
   987→RLS is a security boundary, but policies must also be designed for
   988→performance.
   989→
   990→Guidelines:
   991→
   992→-   Index columns used in ownership checks.
   993→-   Index foreign keys.
   994→-   Keep membership checks efficient.
   995→-   Avoid unnecessarily complex policy expressions.
   996→-   Avoid per-row expensive lookups where a stable authorization helper
   997→    can be used.
   998→-   Test important queries with realistic data.
   999→
  1000→Indexes should be added based on actual access patterns rather than
  1001→blindly indexing every column.

  1008→

  1013→organization_id + updated_at
  1014→organization_id + slug

  1016→
  1017→For relationship tables:
  1018→
  1019→``` text

  1029→# 36. Unique Constraints
  1030→
  1031→Examples:
  1032→
  1033→``` text
  1034→organizations.slug
  1035→(organization_id, user_id)
  1036→(organization_id, domain_id)
  1037→(organization_id, module_id)
  1038→(team_id, membership_id)
  1039→(role_id, permission_id)
  1040→(membership_id, role_id)
  1041→```
  1042→
  1043→Unique constraints must reflect tenant scope.
  1044→
  1045→A business slug that is only unique inside an organization should not be
  1046→made globally unique accidentally.
  1047→
  1048→------------------------------------------------------------------------
  1049→
  1050→# 37. Deletion Strategy
  1051→
  1052→We will avoid broad cascading deletes on important business data.
  1053→
  1054→Preferred strategies:
  1055→
  1056→-   Soft archive for major business entities
  1057→-   Explicit deletion workflows
  1058→-   Restricted foreign keys where accidental deletion is dangerous
  1059→-   Cascades only where the child has no independent meaning
  1060→
  1061→Examples:
  1062→
  1063→Deleting an organization should **not** accidentally destroy production
  1064→business data without an explicit lifecycle process.
  1065→
  1066→------------------------------------------------------------------------

  1072→``` text

  1160→# 42. Database Migration Strategy

  1162→All schema changes must be migration-based.
  1163→
  1164→Never rely on manually editing production databases.
  1165→
  1166→Migration lifecycle:
  1167→
  1168→``` text

  1170→ ↓
  1171→Migration
  1172→ ↓
  1173→Local/Test
  1174→ ↓
  1175→Validation
  1176→ ↓
  1177→Review
  1178→ ↓
  1179→Production
  1180→```

  1183→
  1184→-   Versioned
  1185→-   Repeatable in controlled environments
  1186→-   Reviewable
  1187→-   Reversible where practical
